# 把 public 部署到 B 机（公网方案）

> 结论先行：B 机（北京轻量 2C2G）只跑一个 public 容器，通过公网访问 A 机（杭州 ECS）的 MySQL / Redis / Eureka，网关仍在 A 机，靠注册中心把请求分到两台 public 上。
>
> 两个服务器不同类型的机器（ECS vs 轻量）**内网不互通**，已由阿里云客服确认，因此只能走公网 + IP 白名单。

## 1. 目标拓扑

```
               访客
                │ 80
        ┌───────┴────────┐
        │  nginx（A）     │
        │  gateway（A）   │   ← 从 eureka 名册里拿到两台 public
        │  eureka（A）    │      轮询转发
        │  mysql / redis（A）│
        └───┬────────┬───┘
    172.x│        │ 公网 47.99.174.185:8081
        │        │
   public(A)   public(B)  ← B 公网 IP:8081
   查库→本机    查库→公网回 A（约 30ms）
```

- 两台 public 在 eureka 里是**同名服务下的两个实例**（`BLOG-PUBLIC-SERVICE`）
- A 机副本注册私网 `172.x`，B 机副本注册公网 IP，网关分别直连，不需要任何特殊处理
- 访客入口永远只有一个：A 机的 80

## 2. A 机要改的三处

### 2.1 安全组放行三个端口（控制台手点）

| 端口 | 用途 | 授权对象 |
|---|---|---|
| 3306 | MySQL | `B 公网 IP/32` |
| 6379 | Redis | `B 公网 IP/32` |
| 8761 | Eureka | `B 公网 IP/32` |

**只填 /32 的具体 IP，不要填网段、不要填 0.0.0.0/0。** 跨机器时安全组是唯一防线。

### 2.2 `deploy/compose-main.yml` 增加端口映射

三个服务各加一段 `ports`：

```yaml
  mysql:
    ports:
      - "3306:3306"          # 新增

  redis:
    ports:
      - "6379:6379"          # 新增

  eureka:
    ports:
      - "8761:8761"          # 新增
```

注意：这三个容器会被**重建**（数据在命名卷里，不会丢），mysql 会有 5~15 秒不可用，挑低峰做。

### 2.3 密码（强烈建议）

现在 `root1234` 只在内网用，风险可控；一旦 3306/6379 对外，**白名单是唯一屏障**，密码必须换。要换的话，A 上 `mysql` / `redis` 服务 + `public` / `admin` / `migration` 的 env 共 6 处要同步改。

不换也能跑，但这是唯一一件“建议一次做对”的事。

## 3. B 机部署步骤

### 3.1 装 Docker（一次）

```bash
curl -fsSL https://get.docker.com | sh -s -- --mirror Aliyun
systemctl enable --now docker
docker version && docker compose version
```

### 3.2 登录 ACR（一次）

```bash
docker login crpi-f7ypz0n6qfy16uva.cn-beijing.personal.cr.aliyuncs.com
# 用户名填阿里云账号，密码填 ACR 的固定密码
```

### 3.3 连通性自检（先于启动容器）

```bash
B_PUBLIC_IP=$(curl -s ifconfig.me); echo $B_PUBLIC_IP
nc -vz 47.99.174.185 3306
nc -vz 47.99.174.185 6379
nc -vz 47.99.174.185 8761
```

三条都要通。不通就是 A 的安全组没配好，别往下走。

### 3.4 写 compose（`/opt/blog-worker/docker-compose.yml`）

仓库里已有一份可直接用的 `deploy/compose-worker.yml`（IP 已填好），复制过去即可：

```bash
# 在本地仓库目录执行
scp deploy/compose-worker.yml root@47.94.110.198:/opt/blog-worker/docker-compose.yml
```

或者直接复制下面内容粘贴：

```yaml
# B 机专用：只跑一个 public 副本，不跑 mysql/redis/eureka/gateway/nginx
# 数据源、Redis、注册中心全部指向 A 机的公网地址
services:
  public:
    image: crpi-f7ypz0n6qfy16uva.cn-beijing.personal.cr.aliyuncs.com/ckaicraft/aimcc-blog-public:latest
    ports:
      - "8081:8081"     # 供 A 机的网关访问
    environment:
      # 数据源 → A 机公网 IP
      SPRING_DATASOURCE_URL: "jdbc:mysql://47.99.174.185:3306/aimcc_blog?serverTimezone=Asia/Shanghai&characterEncoding=utf8"
      DB_USERNAME: blog
      DB_PASSWORD: root1234
      SPRING_DATA_REDIS_HOST: "47.99.174.185"
      SPRING_DATA_REDIS_PORT: 6379
      REDIS_PASSWORD: root1234
      # 注册中心 → A 机公网
      EUREKA_URL: "http://47.99.174.185:8761/eureka"
      # 关键：不写这两行会注册容器内的 172.x，A 机网关永远连不上
      EUREKA_INSTANCE_IP_ADDRESS: "47.94.110.198"
      EUREKA_INSTANCE_NON_SECURE_PORT: 8081
      SPRINGDOC_ENABLED: "false"
    healthcheck:
      test: ["CMD", "wget", "-q", "-O-", "--timeout=3", "http://127.0.0.1:8081/api/actuator/health"]
      interval: 10s
      timeout: 5s
      retries: 6
      start_period: 30s
    restart: unless-stopped
```

三点必须遵守：

- **不能写 `container_name`**（不然以后想扩副本会冲突）
- **不能写 `depends_on`**（本机没有 mysql/redis/eureka 服务可依赖，写了直接报错）
- `EUREKA_INSTANCE_IP_ADDRESS` **必须显式写公网 IP**，这是本方案最容易漏的一行

### 3.5 轻量防火墙（控制台手点）

| 端口 | 来源 |
|---|---|
| 22 | 你自己的 IP |
| 8081 | `47.99.174.185`（A 机） |

不要开“全部端口”。

### 3.6 启动

```bash
cd /opt/blog-worker
docker compose pull public
docker compose up -d public
docker compose logs -f public
```

日志里出现这两行就算成功：

```

```

## 4. 验证清单

| # | 在哪做 | 命令 / 观察 | 期望 |
|---|---|---|---|
| 1 | 本机 | `curl -s http://47.99.174.185:8761/eureka/apps` 搜 `BLOG-PUBLIC-SERVICE` | 2 个 instance，`ipAddr` 一个是 `172.x`，一个是 B 的公网 IP |
| 2 | A 机 | `curl -s http://<B 公网 IP>:8081/api/actuator/health` | `{"status":"UP"}` |
| 3 | 本机 | `for i in $(seq 10); do curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://47.99.174.185/; done` | 全 200，耗时呈两档（约 0.2s / 0.4s） |
| 4 | B 机 | `docker compose stop public`，随即连打 10 个请求 | 出现 500（网关仍轮询到已停实例），约 90 秒后全恢复 200 |
| 5 | B 机 | `docker compose start public` | 45 秒内名册恢复 2 条 |

第 4 步是这套机制最真实的表现：**Eureka 是 AP 的，摘除有延迟，窗口内请求会失败**。之前本地验证过同样的现象，跨机器也一样。

## 5. 会踩的坑

1. **B 注册成 172.x**：漏了 `EUREKA_INSTANCE_IP_ADDRESS`。现象是名册里有实例，但网关请求一半 500。
2. **安全组填了网段**：填 `B 的公网 IP/32`，不是 `/24`。
3. **轻量防火墙忘了 8081**：名册正常（注册是 B 出网，不受防火墙影响），但 A 网关连不进来，表现同样是 500。
4. **A 的安全组改了但容器没重建**：端口映射写在 compose 里，必须 `docker compose up -d mysql redis eureka` 才生效。
5. **2G 内存**：public 约 330MB，系统 + Docker 约 500MB，余量够。但别在 B 上再开别的服务。
6. **磁盘 40G**：每次发版拉新镜像，旧层不自动清。定期 `docker image prune -f`。
7. **跨公网 30ms**：一半请求会明显变慢。这是这台北京机器放业务副本的固有代价，不是配置错误。

## 6. 回滚

```bash
# B 机
cd /opt/blog-worker && docker compose stop public
# 约 90 秒后名册只剩 A 的实例，线上回到单机状态
```

A 机那三个端口映射可以留着（有白名单），想彻底收回就删掉三行再 `docker compose up -d mysql redis eureka`。

## 7. CI 要不要接

这次**先手动**，理由：B 机是长期闲置备用机，接进 CI 会让每次发版都动它，收益低、出错面大。

等你确定“B 机常态承载业务”时再接，改法是把 B 也加进 `deploy.yml` 的部署步骤，用 ssh 单独跑一段 `docker compose pull public && up -d public`，需要 B 机的 SSH 私钥进 GitHub Secrets。

## 8. 这套拓扑对“以后 A 到期”的意义

现在的配置已经是 env 驱动的（地址全在 compose 的 `environment` 段），所以将来重排不需要改代码：

- **A 到期、换成小机器**：把 mysql/redis 一起搬到 B，A 只留 nginx + gateway + eureka（约 500MB，1G 机器够），跨机只剩“网关转发”一跳
- **B 到期、换新机**：改 B 的 compose 里那 4 个地址 + `EUREKA_INSTANCE_IP_ADDRESS`，其他不动

唯一的硬约束是：**任何时候，网关所在的机器必须能访问到所有业务副本的 8081/8082，业务副本必须能访问数据库。**

## 9. 已确认的参数

- B 机公网 IP：`47.94.110.198`（本文档与 `deploy/compose-worker.yml` 已填入）
- 本次**不改** MySQL / Redis 密码，先跑通；后续单独一次改（改的时候 A 上 mysql/redis 服务 + public/admin/migration 共 6 处 env 要同步）
- A 机 mysql/redis 重建会带来 5~15 秒不可用，需挑低峰

## 10. CI 的一个注意点（重要）

CI 的部署步骤只点名了 `eureka gateway public admin`：

```
docker compose pull migration eureka gateway public admin && docker compose up -d --remove-orphans eureka gateway public admin
```

含义：

- **`eureka` 会被 CI 重建**，所以它的端口映射在下次部署时自动生效（期间名册会短暂清空，约 90 秒恢复）
- **`mysql` / `redis` 不会被 CI 重建**，端口映射必须在 A 机上手动执行一次 `docker compose up -d mysql redis` 才会生效

不手动执行的话，最典型的现象是：B 机 `nc -vz 47.99.174.185 3306` 不通，但安全组明明已经放行。

## 11. 实测结果（2026-11-24，已验证通过）

### 11.1 注册

Eureka 名册 `BLOG-PUBLIC-SERVICE` 两条实例，均为 `UP`：

```
e47a196cffa4:blog-public-service:8081   ipAddr=172.18.0.5       （A 机容器私网）
b62391f627e4:blog-public-service:8081   ipAddr=47.94.110.198    （B 机公网）
```

### 11.2 性能差异

从外网连续请求 `/api/articles` 10 次，耗时稳定呈两档：

| 来源 | 耗时 |
|---|---|
| A 机副本（同机查库） | 约 0.18 ~ 0.27 秒 |
| B 机副本（跨公网查库） | 约 0.36 ~ 0.40 秒 |

差值约 0.15 秒，来源是每次查库一次杭州↔北京往返（约 30ms）的累积。

### 11.3 故障摘除

B 机 `docker compose stop public` 后立刻请求 10 次：

```
500 200 500 200 500 200 500 200 500 200
```

约 90~120 秒后（Eureka 90 秒租约 + 网关 30 秒缓存刷新）请求全部恢复 `200`。
`docker compose start public` 后名册在 45 秒内恢复两条实例，请求恢复两档耗时。

失败表现为 **500 而非 502**：502 是 nginx 认为网关不可用；500 说明网关正常、只是它连的后端拒绝服务。

### 11.4 端口与网络

- A 机 ECS 安全组入方向放行 `3306` / `6379` / `8761`，来源均为 `47.94.110.198/32`
- B 机轻量防火墙放行 `8081`，来源 `47.99.174.185/32`（80 / 443 已关闭，B 不跑 nginx）
- B 机连接 A 机三个端口的自检写法（不依赖 nc）：

```bash
for p in 3306 6379 8761; do
  timeout 3 bash -c "echo > /dev/tcp/47.99.174.185/$p" 2>/dev/null && echo "$p OK" || echo "$p FAIL"
done
```

### 11.5 卷名统一（顺带完成）

- `deploy/compose-main.yml` 的卷名改为 `blog-mysql-data`，与本地 `docker-compose.yml` 一致
- 迁移时库里本就没有业务数据，所以没做数据复制：mysql 用新空卷重建，镜像 entrypoint 自动建库建用户，Flyway 的 `V1` / `V2` / `V4` 灌入种子数据
- 旧卷 `blog-compose_blog-mysql-data` 确认挂载关系后删除

### 11.6 遗留

- ACR 固定密码重置过，需确认 GitHub Secrets 的 `ACR_PASSWORD` 已同步更新，否则下次 CI 推送镜像会在 `Login to Aliyun ACR` 步骤失败
- B 机不进 CI，发版时 B 机副本仍跑旧镜像；要跟随发版需手动 `docker compose pull public && docker compose up -d public`
