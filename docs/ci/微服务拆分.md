## 二、为什么要把 Flyway 从 admin 里拿出来

### 原来的问题

admin 启动时跑 Flyway，意味着三件事绑在一起：**数据库迁移**、**admin 服务存活**、**admin 的启动顺序**。
只要迁移失败，admin 起不来；admin 多副本时会有多个实例抢着跑同一批脚本（Flyway 有锁，但会把启动时间拖长、报错更难读）；
想单独补一次迁移，只能把整个 admin 拉起来。

### 选的做法：一次性 job 容器

`server/blog-migration` 是一个**只跑完就退出**的模块：依赖只有 flyway-core / flyway-mysql / mysql-connector-j / logback，没有 Spring Web，打出来的 jar 7.1MB。

```yaml
migration:
  image: .../aimcc-blog-migration:latest
  restart: "no"                      # 跑完就退，不是常驻服务
  depends_on:
    mysql:
      condition: service_healthy
```

public / admin 则改成等它跑完：

```yaml
depends_on:
  migration:
    condition: service_completed_successfully
```

`service_completed_successfully` 和 `service_started` 的区别就在这里：前者要求容器**以 0 退出**才算满足，
所以迁移失败时业务容器根本不会启动，不会出现“服务起来了但表结构是旧的”。

迁移主类里两处和“已有库”有关的配置：

```java
.baselineOnMigrate(true)      // 库里已有表但没有 history 表时，直接打基线而不是报错
.baselineVersion("1")         // 把现状视为 V1 已执行过
.connectRetries(10)           // mysql 容器 healthy 了但还没完全可连的情况兜一下
```

### 一个必须记住的坑：`mvn package` 不清 target

脚本用 `git mv` 搬到新模块后，admin 的 `target/classes/db/migration` 里**还留着上一轮编译的 5 个脚本**，
`package` 不 clean 就会把它们打进 admin 的 jar，看起来“剥离了”，实际没剥离。

判断是否真的干净，看 jar 里的条目数：

```bash
unzip -l server/blog-admin-service/target/*.jar | grep -c "db/migration"   # 必须是 0
unzip -l server/blog-admin-service/target/*.jar | grep -c flyway          # 必须是 0
```

所以结论是：**改依赖或资源目录之后，一律 `clean package`**。

## 三、两个服务的接口文档为什么冲突

### 问题

public 和 admin 都默认把文档放在 `v3/api-docs`。两个服务都挂在网关的 `/api` 前缀下，
请求 `/api/v3/api-docs` 时网关按路由规则只会分给 public，admin 的文档**永远拿不到**。
更麻烦的是 admin 的文档里全是写接口，暴露出去等于把管理 API 的入参出参一起公开。

### 四类常见做法

| 做法 | 说明 | 适用 |
|---|---|---|
| 各自独立路径 | 每个服务把文档挪到自己的前缀下 | 服务少、内网/单机，最简单 |
| 网关文档门户 | 网关聚合成一个入口（springdoc 聚合、或 Knife4j 网关聚合） | 服务多、需要一个统一入口 |
| 独立 API 平台 | 文档不跟服务走，构建时导出 JSON 交给 Apifox/YApi | 团队协作、要版本管理 |
| 生产关闭 | 线上彻底不注册文档端点 | 任何对外环境都该做 |

本次选**各自独立 + 生产关闭**：服务只有两个，聚合门户的收益不值这份复杂度。

### 具体改动

admin（路径分离 + 开关）：

```yaml
springdoc:
  api-docs:
    path: /admin/v3/api-docs        # 实际 URL = context-path(/api) + 这段
    enabled: ${SPRINGDOC_ENABLED:true}
  swagger-ui:
    path: /admin/swagger-ui.html
    enabled: ${SPRINGDOC_ENABLED:true}
```

public 只加开关，路径不动（`/api/v3/api-docs`）。

生产 `deploy/compose-main.yml` 里两个服务都设 `SPRINGDOC_ENABLED: "false"`。

### 两个反直觉的点

**1. 光挪路径不够，还会被 Sa-Token 拦成 401。**
admin 的拦截器是 `/admin/**` 全量校验，文档请求不带 token，于是 401。放行名单要补：

```java
.excludePathPatterns("/admin/login",
    "/admin/v3/api-docs", "/admin/v3/api-docs/**",
    "/admin/swagger-ui.html", "/admin/swagger-ui/**");
```

放行不等于暴露：生产用 `SPRINGDOC_ENABLED=false` 把端点整个关掉，401 和 404 都不会出现。

**2. admin 的 Swagger UI 不要走网关。**
`path` 改的是页面本身，UI 的 JS/CSS 仍在 `/api/swagger-ui/**`，网关会把它分给 public，
页面打开就是白屏。UI 直连端口访问即可：`http://localhost:8082/api/admin/swagger-ui.html`。
**JSON 可以走网关**（`/api/admin/v3/api-docs`），UI 不行。

**3. 看状态码会误判。**
项目全局异常处理器把 404 也包成 HTTP 200 + `{"code":404,"message":"路径未找到"}`，
所以验证时必须看 body，不能只看 `curl -I`。

## 四、请求链路：nginx 与网关谁管哪一段

### 一个请求的完整路径

```
浏览器
  └─ nginx :80
       ├─ /            → 博客静态站（Astro 产物，直接吐文件）
       ├─ /admin/      → 后台 SPA（Vite 产物，history 路由回退 index.html）
       └─ /api/        → gateway :8080
                          ├─ /api/admin/**  （order: -1，优先命中）
                          │     → admin   :8082
                          └─ /api/**        （兜底）
                                → public  :8081
                                      ↓
                                 mysql :3306 / redis :6379
```

三条容易记错的规则：

- **nginx 只做两件事**：吐静态文件、把 `/api` 交给网关。它不直接连 public/admin。
- **前缀一路不剥离**。两个服务的 `context-path` 都是 `/api`，nginx 原样转、网关原样转，
  最后由 `@RequestMapping("/api/...")` 接住，中途没有任何一层删前缀。
- **admin 路由必须排在前面**。`/api/admin/**` 同时能匹配 `/api/**`，靠 `order: -1` 压到最优先，不依赖 YAML 书写顺序。

### 分层约定

| | nginx | gateway |
|---|---|---|
| 本质 | C 写的反向代理，面向“站点与连接” | Java 应用（Spring Cloud Gateway，跑在 JVM 里） |
| 擅长 | TLS 终止、静态文件、连接复用、扛大并发 | 按业务维度路由与治理 |
| 认识的“路由” | 路径前缀、正则、Host、Header | 同上，还能读请求体、改写请求、挂过滤器链 |
| 鉴权 | 只懂 basic auth / IP 白名单，不认自己的 token | 能写过滤器统一校验 Sa-Token、把用户 ID 塞进请求头 |
| 限流 | 按 IP / 连接数 | 按用户、按接口、按租户 |
| 改路由的代价 | **nginx.conf 打进前端镜像，改一行就要重建前端镜像并重新发版** | 路由跟着后端服务走，独立发布 |

最后一行是这次把路由交给网关的实际理由：`nginx.conf` 是 COPY 进前端镜像的，
改一条路由跟前端代码毫无关系，却要把整套前端重新构建、推镜像、发版。
服务还会继续加，这条路走不通。

约定：**nginx 只管“对外入口 + 静态资源”，路径一旦进了 `/api/`，路由决定权全在网关，nginx 不再判断。**

### 一个已经退化掉的能力：多副本轮询

`2026-11-12`（提交 `9198464`）为了让后端能水平扩容，nginx 里做过一套多副本分发：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;   # Docker 内置 DNS，10 秒刷新

location /api/ {
    set $backend "http://server:8080";     # 用变量，而不是直接写域名
    proxy_pass $backend;
    add_header X-Upstream $upstream_addr always;   # 响应头里回显真正命中的副本
}
```

两个关键点：**直接写域名时 nginx 只在启动时解析一次**，多副本也永远只打一个；
换成变量之后，每次请求都按 resolver 的结果分发，多个 IP 自然轮询。
当时用 `X-Upstream` 响应头就能看出两条请求落到了不同实例。

`2026-11-20` 拆分（提交 `e25e3f7`）时，上游从 `server:8080` 改成 `gateway:8080`，这套逻辑原样保留，
但网关至今仍是 1 副本，所以 nginx 这一层实际没在工作。

> **2026-11-25 更新：真正的下一跳已经改掉了。**
>
> 网关路由原来写死 `http://public:8081`（静态 URI，JVM 解析一次 DNS 就缓存，多副本也只会打到同一个实例）。
> 现在改成服务名 + 注册中心：
>
> ```yaml
> - id: public-api
>   uri: lb://blog-public-service      # 名字 = 后端的 spring.application.name
>   order: 0
> ```
>
> 配套动作：Eureka 上线；public / admin 用 `EUREKA_INSTANCE_IP_ADDRESS` 明确注册自己的 IP（容器内主机名不一定可解析）；网关每次转发从名册里挑一个实例。
>
> 所以「多副本要靠网关这一跳才生效」这句话现在成立了，而且 public 已经真的有两个实例：A 机 1 个 + B 机 1 个，跨机也被纳入轮询。
>
> 代价是负载均衡不区分机器远近：一半请求会被打到 B 机，每次多约 30ms 公网往返。Eureka 没有权重概念，要按机器/机房分级只能自己写 filter，或者接受这个损耗。
>
> 附带的新单点：**Eureka 和网关都只有一份，且都在 A 机**。Eureka 挂了 → 网关查不到实例 → 所有 `lb://` 路由失效；网关挂了 → 整个 `/api` 不可用。这两条记在第七节。

## 五、部署链路的坑

### 新仓库第一次推镜像会卡死

新建 `aimcc-blog-migration` 仓库第一次 push，要传 225MB 的 JRE 基础层，CI 卡在 `Push backend images` 45 分钟，
日志是 `failed to copy: ... blobs/uploads ... use of closed network connection`。

已加的重试（提交 `8398a75`）：`push_with_retry` 包一层，最多 5 次、每次间隔 20s，
已上传的层会被跳过，重试等价于断点续传。

真卡住时的救急办法：**本机先推**。ACR 支持跨仓库复用层（日志里 `Mounted from ckaicraft/aimcc-blog-gateway`），
同架构的基础层不用重传，所以本机推只花了 10 秒，之后 CI 再推就是全命中缓存。

### ACR 仓库不用手动建

四个后端仓库（gateway / public / admin / migration）+ 前端 `aimcc-blog-nginx` 都是 **push 时自动创建**，
命名空间 `ckaicraft` 事先存在就行。报 401/`repository not found` 先怀疑登录凭据，不是先怀疑没建仓库。

### 镜像为什么“带 id”和“不带 id”

CI 每个镜像打两个 tag：

```bash
docker build -t $IMAGE:latest -t $IMAGE:${{ github.sha }} ...
```

所以 ACR 上的镜像带 commit sha，回滚时直接 `:$sha` 拉回来。
本地手工构建如果只写 `-t repo:v1`，同一个 tag 被反复覆盖，旧镜像就变成一堆 `<none>` dangling。
本地想留痕就多打一个：`-t repo:v1 -t repo:$(git rev-parse --short HEAD)`。

### 别忘的两件小事

- CI 失败先看是哪一步、再看本地能不能复现。今天有一次 `Build backend jar` 在 runner 上挂了 5 分钟，
  本地同一句 `mvn clean package -DskipTests` 是 BUILD SUCCESS，判定为依赖拉取抖动，重跑即过。
- 服务器是关机状态的话，`Add server to known hosts` 必然失败，这跟代码无关。
- 想重触发一次部署，推个空提交就行：`git commit --allow-empty -m "ci(deploy): ..."`。
  但旧 run 不会自己停，卡住的要在 Actions 页面手动 Cancel，不要两个 run 同时 deploy。

## 八、还没弄懂、留着自己补的知识

| 知识点 | 触发场景 | 以后要弄明白什么 |
|---|---|---|
| Maven `provided` 作用域 与 JVM 类加载时机 | 把 `GlobalExceptionHandler` 合并到 `blog-common` 时，`spring-webmvc` 用 `provided` 引，网关 jar 里没有这个包却能正常启动 | “类的符号引用什么时候才真正解析”这一段没吃透：为什么类躺在 classpath 里没人加载就没事、Spring 扫描包时读注解为什么就会 `NoClassDefFoundError`、`provided` 和 `optional` 到底差在哪。等以后遇到 `ClassNotFoundException` / `NoClassDefFoundError` 时专门学一遍 |
| JVM 类加载的双亲委派与懒解析 | 同上 | 加载 → 链接（验证/准备/解析）→ 初始化的时序，以及“解析可以延迟到首次使用” |
