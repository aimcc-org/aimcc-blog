# 多机部署变更方案（2026-11-24）

> 目标：让 `public` 跑在第二台机器（B 机）上，A 机的网关把它当普通副本轮询。
> 本文回答「到底要改什么」，操作细节见《多机部署清单-2026-11-23.md》。
> 状态：只做方案，暂不执行。

---

## 0. 一句话

**Java 代码、网关路由、nginx 配置全部不用改。** 需要动的只有三个地方：

| 位置 | 改什么 | 是否必须 |
|---|---|---|
| A 机 `deploy/compose-main.yml` | eureka / mysql / redis 各加一行 `ports`，绑定到内网地址 | 必须 |
| B 机新建 `/opt/blog-public/docker-compose.yml` | 只含 public 一个服务，约 25 行 | 必须 |
| `.github/workflows/deploy.yml` | 加一步「部署到 B 机」 | 可选（手工部署也能跑） |

另外 B 机要装 Docker、登录 ACR，这属于环境准备，不算代码变更。

---

## 1. 先选网络模式（决定后面所有 IP 怎么填）

| 模式 | 适用 | 优点 | 代价 |
|---|---|---|---|
| **A. 同厂商同 VPC** | 再买一台阿里云 | 内网直连，延迟低，安全组管得住 | 要花钱 |
| **B. 跨厂商 + Tailscale** | 用腾讯免费试用机 | 零成本，不暴露任何端口到公网 | 多装一个客户端，多一层虚拟网 |
| **C. 跨厂商 + 公网白名单** | 临时验证 | 不装额外软件 | 3306/6379 对公网开放，风险高，不推荐 |

推荐 **A**（长期）或 **B**（练手）。下文用 `B_ADDR` 代表「A 机访问 B 机时用的地址」：

- 模式 A：`B_ADDR = 192.168.x.x`（B 机内网 IP）
- 模式 B：`B_ADDR = 100.x.x.x`（B 机的 Tailscale IP）

## 2. A 机改动（1 个文件，3 处）

文件：`deploy/compose-main.yml`

### 2.1 eureka 加端口

```yaml
  eureka:
    image: .../aimcc-blog-eureka:latest
    ports:
      # 绑定到内网/虚拟网地址，而不是 0.0.0.0：
      # 只允许同网段的 B 机访问，公网扫不到
      - "192.168.1.10:8761:8761"      # 模式 A
      # - "100.64.1.10:8761:8761"     # 模式 B（换成 A 机的 Tailscale IP）
```

### 2.2 mysql 加端口

```yaml
  mysql:
    ports:
      - "192.168.1.10:3306:3306"
```

### 2.3 redis 加端口

```yaml
  redis:
    ports:
      - "192.168.1.10:6379:6379"
```

> 三处都绑定到具体 IP，不写 `0.0.0.0`。这样即使安全组配错，公网也连不上。
> 绑定后需要重建容器：`docker compose up -d eureka mysql redis`（约 20 秒中断，
> 建议低峰执行；registry 重启会有约 90 秒名单重建窗口）。

### 2.4 不需要改的

- `server/blog-gateway/src/main/resources/application.yaml`：路由已是 `lb://服务名`
- `server/blog-public-service/.../application.yaml`：注册地址来自 `EUREKA_URL` 环境变量
- `docker/nginx/nginx.conf`：仍然只指向 A 机的 gateway
- 任何 Java 代码

## 3. B 机新增（1 个文件）

目录 `/opt/blog-public/`，文件 `docker-compose.yml`：

```yaml
services:
  public:
    image: crpi-f7ypz0n6qfy16uva.cn-beijing.personal.cr.aliyuncs.com/ckaicraft/aimcc-blog-public:latest
    restart: unless-stopped
    ports:
      # 只绑 B_ADDR：A 机的网关要能连进来，公网连不上
      - "192.168.1.20:8081:8081"        # 模式 A 写 B 机内网 IP；模式 B 写 100.x
    environment:
      # ---- 数据源：全部指向 A 机 ----
      SPRING_DATASOURCE_URL: "jdbc:mysql://192.168.1.10:3306/aimcc_blog?serverTimezone=Asia/Shanghai&characterEncoding=utf8"
      DB_USERNAME: blog
      DB_PASSWORD: root1234
      SPRING_DATA_REDIS_HOST: 192.168.1.10
      SPRING_DATA_REDIS_PORT: 6379
      REDIS_PASSWORD: root1234
      # ---- 注册中心 ----
      EUREKA_URL: "http://192.168.1.10:8761/eureka"
      # 关键两行：不写就会注册成容器内网 172.x，A 机网关连不上
      EUREKA_INSTANCE_IP_ADDRESS: "192.168.1.20"
      EUREKA_INSTANCE_NON_SECURE_PORT: "8081"
    healthcheck:
      test: ["CMD", "wget", "-q", "-O-", "--timeout=3", "http://127.0.0.1:8081/api/actuator/health"]
      interval: 10s
      timeout: 5s
      retries: 6
      start_period: 30s
```

四点注意：

1. **不要写 `depends_on:`**，B 机没有 mysql / redis / migration，写了直接起不来
2. **必须映射 8081**，否则注册了地址也没人连得进去
3. **必须显式 `EUREKA_INSTANCE_IP_ADDRESS`**，这是跨机器第一大坑
4. B 机不需要 clone 仓库、不需要 nginx、不需要 gateway、不需要 eureka

启动：

```bash
docker login crpi-f7ypz0n6qfy16uva.cn-beijing.personal.cr.aliyuncs.com
cd /opt/blog-public && docker compose up -d
```

## 4. CI 改动（可选）

两选一：

**做法一：手工部署（先这样）**

CI 只负责构建推送镜像，B 机发版时手动执行两条命令。适合发版频率低的情况。

**做法二：加第二个部署目标**

在 `.github/workflows/deploy.yml` 的 `Deploy backend` 后面加：

```yaml
      - name: Deploy public to second host
        run: |
          ssh root@${{ secrets.SERVER_IP_B }} \
            "cd /opt/blog-public && docker compose pull public && docker compose up -d public"
```

需要新增：

- secret `SERVER_IP_B`
- secret `SSH_PRIVATE_KEY_B`（单独一把钥匙，别复用）
- B 机上也执行一次 `docker login`（凭据存在 `~/.docker/config.json`，与 CI 无关）

**这一步不是必须的。** 没有它，B 机靠手动 pull 也能正常跑。

---

## 5. 发布顺序（重要）

多机之后，两台机器上的镜像版本可能不一致，而 Flyway 迁移只在 A 机跑。顺序建议：

```
1. 迁移 + A 机 public 升级（新版本先在一个副本上验证）
2. 观察 1~2 分钟，接口 200
3. 再升级 B 机 public
```

反过来（先升 B 再迁库）会出现「新代码跑在旧表结构上」；同时升级两台则失去了「先验证一个副本」的意义。

如果不想管顺序，最简单的做法是**发版时先 `docker compose stop public` 停掉 B 机**，等 A 机升完再拉起。

## 6. 验收标准

| 检查项 | 命令（在 A 机执行） | 期望 |
|---|---|---|
| B 机已注册 | `curl -s localhost:8761/eureka/apps \| grep ipAddr` | 出现 `B_ADDR`，状态 `UP` |
| 网关能打通 | 连发 10 次 `curl -s -o /dev/null -w "%{http_code}" localhost/api/articles?page=1&size=1` | 10 个 `200` |
| 公网入口不变 | `curl -I http://47.99.174.185/` | `200`，且只有一个 IP 对外 |
| 摘除正常 | 停 B 机 public，等 100 秒再请求 | 先出现部分 500，之后全 200 |
| 会话共享 | 在站点登录后刷新 | 不掉登录态（说明共用 A 机 Redis） |

## 7. 回滚

```bash
# B 机
cd /opt/blog-public && docker compose down
```

90 秒内名册自动剔除 B 机实例，网关回到只打 A 机。**不需要改任何配置或代码。**

如果 A 机端口暴露后想收回：还原 `deploy/compose-main.yml` 的备份（CI 每次部署会留 `.bak`），
`docker compose up -d` 即可。

## 8. 风险与代价

| 风险 | 说明 | 缓解 |
|---|---|---|
| 数据库暴露 | 3306/6379 一旦绑到 `0.0.0.0`，公网可扫 | 只绑内网 IP + 安全组白名单；跨厂商用 Tailscale |
| 版本漂移 | 两机镜像不同版本，表结构变更时可能报错 | 按第 5 节顺序发版，或发版时临时停 B |
| 数据库单点 | 多机只解决了「计算」冗余，MySQL 仍只有一台 | 接受；真要高可用得上主从，是另一件事 |
| 注册中心单点 | 重启有约 90 秒名单为空 | 接受；或以后配第二个 Eureka 做 peer |
| 跨公网延迟 | 每查一次库多几十毫秒 | 博客访问量低可忽略；模式 A 无此问题 |

## 9. 花费与工程量

**机器**：2 核 2G / 40G 盘 / 按量带宽，跑一个 public 足够（实测占约 300MB）。
包年或按量都行，免费试用到期记得迁移。

**时间**：

- A 机改三处 + 重建：约 15 分钟（含 90 秒窗口观察）
- B 机装 Docker + 配 compose + 启动：约 30 分钟（含拉镜像）
- 验收：约 20 分钟
- CI 那一步：约 20 分钟（可选）
