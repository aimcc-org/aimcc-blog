## 一、把第二个前端挂到 /admin/

### 现状

```
front/blog-web      Astro 静态站      → 产物 front/blog-web/dist/main
front/blog-admin    Vite + React SPA  → 产物 front/blog-admin/dist
```

两个产物打进**同一个 nginx 镜像**，博客在 `/`，后台在 `/admin/`。

### 必改的三处

| 文件 | 改动 | 不改的后果 |
|---|---|---|
| `front/blog-admin/vite.config.ts` | `base: command === "build" ? "/admin/" : "/"` | 产物引用 `/assets/xxx.js`，线上 404 白屏 |
| `docker/nginx/nginx.conf` | `location /admin/ { try_files $uri $uri/ /admin/index.html; }` | 刷新 `/admin/drafts` 返回 404 |
| `docker/nginx/nginx.conf` | `location = /admin { return 301 /admin/; }` | 不带尾斜杠时相对路径解析错乱 |

`base` 用 `command === "build"` 判断，不用 `mode === "production"`：是否加前缀取决于「是不是构建」，不取决于模式名，以后加 `--mode staging` 不会丢。

### 为什么后台不用改接口地址

`src/services/request.ts` 里 `baseUrl` 默认是 `/api`（同源绝对路径，相对域名根），token 走 `satoken` 头。
nginx 把 `/api/` 转发给 `server:8080`，所以**挂在哪个路径下都不影响接口**。

### 一个容易误判的现象

`try_files` 让**任何未知路径都返回 200**（实际拿到的是 `index.html`）。
所以浏览器插件探测的 `/default_config.content.json` 也「看起来成功」。
**200 不代表那个文件存在**，看 `Initiator` 列能分辨是不是插件发的。

## 二、镜像瘦身与体积口径

### 改了什么

```dockerfile
# docker/server/Dockerfile
-FROM eclipse-temurin:25-jre
+FROM eclipse-temurin:25-jre-alpine
```

同架构真实收益：`408MB → 280MB`，省 128MB。

### 同一个镜像为什么有四个大小

| 口径 | 命令 | 含义 |
|---|---|---|
| 解压后真实内容 | `docker history <img> --format '{{.Size}}'` 求和 | **唯一可跨环境比较** |
| `inspect .Size` | `docker image inspect -f '{{.Size}}' <img>` | 本地/服务器含义不同，不可跨环境比 |
| 容器内文件占用 | `docker run --rm --entrypoint sh <img> -c "du -sh /"` | 排查「谁占地方」 |
| 本镜像独占 | `docker system df -v` 的 UNIQUE SIZE | 删了能省多少 |

`docker images` 里的 `DISK USAGE 400MB` 是假象：

```
400MB = 压缩 blob 121MB（CONTENT SIZE） + 解压快照 ~280MB
```

containerd 把两份都存了，不是镜像真的大了。

### 踩坑

- `docker run <img> du -sh /` 会把 `du` 当参数送给 `java -jar`，必须 `--entrypoint sh` 覆盖。
- **跨架构比较无效**：拿 arm64 的 407MB 和 amd64 的 276MB 比得出「省 250MB」是错的。
- Spring Boot 280MB 属正常，jlink 裁剪性价比低，到此为止。

### 验证基础镜像真的换了

```bash
docker history <img> --format '{{.Size}}\t{{.CreatedBy}}'
```

看到 `ADD alpine-minirootfs-...` 和 `apk add` 才算数；出现 `apt-get` / `dpkg` 说明还是 Ubuntu 底。

## 三、服务器 compose 纳入 git

### 问题

服务器 `/opt/blog-compose/docker-compose.yml` 手工维护、不在 git 里，和本地那份已经不一致：

| | 本地 `docker-compose.yml` | 服务器那份 |
|---|---|---|
| 镜像来源 | `build:` 本地构建 | ACR 拉取 |
| mysql/redis 端口 | `3307:3306` / `6379:6379` | 不暴露 |
| server 端口 | `8080:8080` | 不暴露 |
| restart | 无 | `unless-stopped` |

服务器配置成了没人知道内容的黑盒。

### 做法

```
docker-compose.yml        本地开发（build:）
deploy/compose-main.yml   服务器（image:，进 git）
```

CI 每次部署前同步：

```yaml
- name: Sync compose file
  run: |
    scp deploy/compose-main.yml root@IP:/opt/blog-compose/docker-compose.yml.new
    ssh root@IP "cd /opt/blog-compose && cp docker-compose.yml docker-compose.yml.bak \
      && mv docker-compose.yml.new docker-compose.yml \
      && docker compose config -q"
```

顺序是刻意的：**传临时文件 → 备份 → 替换 → 校验语法**，任一步失败都不碰在跑的配置。

### 红线：项目名与卷名的关系

> Compose 的**项目名默认等于 compose 文件所在目录的文件夹名**，
> **数据卷名 = 项目名 + `_` + 声明的卷名**。

```
目录 /opt/blog-compose  → 项目名 blog-compose  → 卷 blog-compose_blog-mysql-data
```

**目录一改名，前缀就变，Compose 会新建一个空卷**，服务连上空库（数据还在旧卷里，只是没挂上）。

补救：卷名写死。

```yaml
volumes:
  blog-mysql-data:
    name: blog-compose_blog-mysql-data
```

> 通用原则：**带数据卷的 compose，卷名都应该显式 `name:`**。
> 默认前缀机制等于把目录名变成了数据库的唯一标识。

### 怎么验证这次同步没搞坏东西

```bash
cd /opt/blog-compose && docker compose ps
docker volume ls
```

判据：

| 现象 | 含义 |
|---|---|
| mysql/redis 的 CREATED 没变 | ✅ 配置哈希没变，数据安全 |
| server/nginx 被重建 | 镜像 digest 变了，**属于另一回事** |
| 多出 `blog-mysql-data` / `compose_...` 之类新卷 | ❌ 卷名错了，立刻回滚 |

回滚：

```bash
cd /opt/blog-compose && cp docker-compose.yml.bak docker-compose.yml && docker compose up -d
```

**关键区分：容器重建 ≠ 配置变化。** 前者看镜像 digest，后者看配置哈希。

## 四、`rush build` 的退出码不可信

```
Operations succeeded with warnings.
rush build (14.63 seconds)
exit=1
```

`front` 根目录的 `pnpm run build` 实际是 `rush build`。构建成功但退出码 1，原因是项目往 stderr 写了东西：

| 项目 | 警告 | 条数 |
|---|---|---|
| `blog-admin` | antd 的 `"use client"` 指令被忽略 | 307 |
| `blog-web` | Pagefind 不支持 `zh-cn` 词干 | 4 |

Rush 认为「有警告 = 构建不干净」，于是给 1。产物是齐全的：`blog-web/dist/main`、`blog-admin/dist`。

`ELIFECYCLE` 只是 pnpm 说「子进程非 0」，不是它自己出错。

> **判据：看产物，不看退出码。** `dist` 是新的 = 成功；日志里出现 `ERROR:` 才必须查。

这也是 CI 里不用 `rush build`、改成 `cd blog-web && pnpm build` 的原因。

## 五、TS1343：IDE 报错而命令行不报

现象：

```
TS1343: The import.meta meta-property is only allowed when the --module option is es2020...
```

根因不是 `module` 配错了，而是 **`vite.config.ts` 是 tsconfig 的孤儿文件**：`include: ["src"]` 没管它，IDE 用自己的默认（CommonJS）配置解析它。

修法：

```json
{
  "include": ["src", "vite.config.ts"]
}
```

顺手把 `process.cwd()` 换成 `"."`（项目没装 `@types/node`）。

**这类问题的模式**：命令行通过、IDE 报错 → 先怀疑「文件没被项目配置管到」，而不是怀疑类型系统。

## 六、两个小的

**BCrypt 密文长度固定 60。** 改后台密码前先验证：

```sql
SELECT LENGTH(password_hash) FROM admin_user WHERE username = 'ck';
```

长度不对就是密文本身有问题，别怀疑接口。

命令行里 `$2a` 会被 bash 展开成空，所以要 `docker exec -it blog-mysql mysql -uroot -proot1234 aimcc_blog` 进容器再敲 SQL。

**浏览器 Network 里的 `chrome-extension` 是插件噪音**，看 `Initiator` 列就能分辨。

## 七、常用命令备忘

```bash
# 本地构建镜像（必须指定 amd64，Apple Silicon 否则架构不对）
docker build --platform linux/amd64 -f docker/server/Dockerfile -t <tag> ./server

# 单独跑 nginx 镜像时需要补 host，否则解析不了 compose 服务名
docker run --add-host server:127.0.0.1 ...

# 镜像体积（真实内容）
docker history <img> --format '{{.Size}}' | awk '{gsub("MB","");s+=$1} END{print s"MB"}'

# 本地校验 compose
docker compose -f deploy/compose-main.yml config -q
```
